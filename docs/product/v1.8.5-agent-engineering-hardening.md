# ResearchForge V1.8.5 Agent Engineering Hardening

**Status:** COMPLETE — engineering gate + public GitHub CI + Owner re-acceptance PASS.

## Target state

Keep the V1.7 question-driven financial-research truth boundary, while making the project substantially stronger as an Agent engineering system and interview artifact:

1. current, audited dependency/security baseline;
2. explicit Product Agent Eval Harness;
3. deterministic Failure Taxonomy and regression loop;
4. measured Retrieval Benchmark before infrastructure escalation;
5. first-class MCP interface over the same backend;
6. architecture, evidence and CI surfaces that make these decisions inspectable.

## Delivered engineering slices

### V1.8.0 — Security refresh

LangGraph moved from the 0.6 line to 1.x without replacing the bounded `StateGraph` architecture. pypdf and test/security tooling were upgraded; `pip-audit` is a CI gate. API docs are disabled by default, Web receives explicit browser security headers and model capability remains visible on narrow screens.

### V1.8.1 — Agent Eval Harness

`researchforge eval` evaluates a frozen offline component suite and optional persisted product Runs. Persisted successful Runs are scored for intent routing, plan completion, claim grounding, citation validity, structured-output validity and workflow trajectory. Thread evaluation requires one company context and does not fabricate semantic-contradiction scoring.

### V1.8.2 — Failure Analysis

Fourteen deterministic failure classes cover entity resolution, discovery, acquisition, parsing, retrieval, evidence insufficiency, tools, model schema, grounding, citations, timeout, budget, recovery and infrastructure. `researchforge failure-analyze` converts persisted failure metadata into a regression-oriented record without provider calls.

### V1.8.3 — Retrieval Benchmark

The frozen reviewed suite compares current lexical retrieval, a local TF-IDF sparse-vector baseline and a simple reciprocal-rank fusion baseline. Current evidence does not justify pgvector/dense retrieval yet; the benchmark exists specifically to prevent technology-by-fashion decisions.

### V1.8.4 — MCP

The official Python MCP SDK exposes seven bounded tools for company resolution, filing discovery, research submission, persisted result/trace/facts and evidence search. stdio is the default local transport; Streamable HTTP is optional and binds to `127.0.0.1:8001` by default.

### V1.8.5 — Interview / architecture packaging

CI is split into backend, contracts, eval, security, frontend and containers. Versioned V1.8 schemas cover Agent Evaluation, Retrieval Benchmark, Failure Analysis and the MCP toolset. Portfolio and architecture documentation link claims to measured evidence.

## Non-goals

- No multi-agent debate.
- No “self-evolving agent” claim.
- No pgvector/dense retrieval until benchmark evidence supports it.
- No LLM judge presented as ground truth.
- No trading, price target, investment recommendation or portfolio management scope.
- No rewrite of V1.7.3 Run Manifest or V1.7 Research Result history merely to match the product release number.

## Release acceptance

V1.8.5 engineering completion required formatting/lint/strict typing/tests/contracts/eval/security audits/frontend E2E/fresh containers/n8n/MCP/runtime checks, Owner runtime restored to `auto + model_synthesis`, synchronized Git/GitHub state and green public CI. Those engineering conditions passed, and the owner subsequently completed the separate manual product re-acceptance with no release blocker.
